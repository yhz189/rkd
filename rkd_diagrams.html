6二进制通信协议

请求包（Request）— 固定 64 字节

1 byte cmd 命令码
63 bytes name[63] 进程名（\0 结尾）
命令码：1=START   2=STOP   3=RESTART   4=STATUS   5=LIST

响应包（Response）— 固定 128 字节

4 bytes ret_code int，0=成功 -1=失败
124 bytes msg[124] 消息文本（\0 结尾）

9面试高频问答（点击展开）
Q1. 守护进程为什么要 fork 两次？ ▶
第一次 fork() 让父进程退出，子进程调用 setsid() 创建新会话，脱离控制终端，成为会话组长。

但此时子进程是会话组长，如果它打开一个终端设备，内核会自动将其设置为控制终端——又重新有了终端。

第二次 fork() 让最终的守护进程不是会话组长，从根本上断绝了重新获取控制终端的可能。
Q2. 为什么不设置 SA_RESTART？ ▶
设了 SA_RESTART，被信号中断的系统调用会自动重新执行。信号处理函数设完 running=0 后，epoll_wait 不返回 EINTR，而是继续等待——主循环无法及时感知 running=0，退出被延迟。

不设 SA_RESTART：信号一来，epoll_wait 立刻返回 EINTR，下一次 while 判断 running=0 即刻退出，响应及时。
Q3. epoll 比 select/poll 好在哪里？ ▶
select/poll 的问题：每次调用都把整个 fd 集合从用户态拷贝进内核，内核线性扫描所有 fd，O(n) 复杂度。select 还有 FD_SETSIZE=1024 的硬上限。

epoll 的优势：用 epoll_ctl 一次注册 fd，内核维护就绪链表。epoll_wait 只返回真正就绪的 fd，O(1) 复杂度，无 fd 数量上限。
Q4. 为什么用 Unix Domain Socket 而不是 TCP？ ▶
rkd 和 rkctl 都在同一台机器上，没必要走网络协议栈。

• 性能：内核内存拷贝，无 TCP 握手、校验和、拥塞控制开销
• 访问控制：socket 文件有文件权限，可以限制只有特定用户访问
• 简单：路径即地址，无需管理 IP 和端口
Q5. 怎么防止子进程变成僵尸进程？ ▶
监控线程每秒调用 waitpid(pid, &status, WNOHANG) 轮询所有子进程。

子进程一退出，其 PCB 中的退出状态立即被父进程用 waitpid 回收，内核释放 PCB，不会产生僵尸。

WNOHANG 标志保证非阻塞：子进程未退出时立即返回 0，不影响监控线程继续运行。
Q6. 两个线程同时操作进程列表，如何保证线程安全？ ▶
ProcManager 里有一把 pthread_mutex_t lock。主线程处理 IPC 命令和监控线程跑 waitpid 循环，操作 procs[] 前都必须先 pm_lock()，用完立即 pm_unlock()。

特殊处理：handle_crash() 在 sleep(restart_delay) 前临时 pm_unlock()，避免持锁 sleep 阻塞主线程。
Q7. volatile 关键字在这里有什么作用？ ▶
ProcManager.running 声明为 volatile int。

编译器优化可能把频繁访问的变量缓存在 CPU 寄存器里，主循环每次读的是旧值，感知不到信号处理函数对内存的修改。

volatile 告诉编译器：每次读写都必须直接操作内存地址，保证信号处理函数写的 running=0 对主循环立即可见。
Q8. fork 之后为什么子进程用 execvp 而不是 execl？ ▶
配置文件里的命令是运行时读取的字符串，需要动态拆分参数，无法在编译时写死。

execvp 接受 char *argv[] 数组，适合运行时构建参数列表（build_argv() 用 strtok_r 按空格拆分）。

execvp 中的 p 表示会搜索 PATH 环境变量，可以不写绝对路径直接用命令名（如 nginx）。
